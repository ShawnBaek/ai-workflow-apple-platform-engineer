# Changelog

Notable changes to Apple Platform Engineer, in the format of [Keep a Changelog](https://keepachangelog.com/en/1.1.0/). The version label comes from [`VERSION`](VERSION). Versions before 2.0.0-beta.10 were not recorded here; see the Git history.

## [Unreleased]

### Migration

- **Private harnesses: observe `runtime-identity` and the skill bundle again** ([#106], [#110], [#115], [#116], [#117], [#119], [#121]). [#106], [#110], [#115], [#116], [#117], [#119] and [#121] change the verifier's Swift sources (`verification/Sources`), so the source-bundle SHA-256 changes and existing `resource_coordinator` and `authorization_runtime` bindings fail by design; `contracts/` is unchanged. Recover as the 2.0.0-beta.11 Migration item describes: finish or safely recover active leases, [build and locate the verifier](skills/agent-harness/references/swift-verification.md#build-and-locate-the-verifier), run `runtime-identity`, and review and update the private bindings. [#106], [#109], [#110], [#111], [#112], [#115], [#116], [#117], [#118], [#119] and [#121] also change skills that every harness requires (`agent-harness`, `apple-development-health`, `git-workflow` or `github-projects`), so re-derive the digest with `"$APE" --app-root "$APP_ROOT" health --harness '<absolute-private-harness-path>' --observe-agent-skills`, review it, copy the reported `expected_bundle_sha256` into `agent_skills` in the private harness and run the command again, as step 6 of [first setup](skills/agent-harness/references/coordinator-setup.md#first-setup-or-schema-migration) describes, then rerun health and start a new run. [#67] and [#108] change the bundle only for a `runtime_ui` harness, or one whose task skills include `apple-platform-testing`, `code-review` or `apple-platform-performance`, and [#113] only for one whose task skills include `code-review`, `open-xcode-handoff` or `xcode-preview-design`; recover them the same way. Never auto-rehash an approval or rewrite a historical ledger.
- **The skill bundle hash now changes at every release** ([#110]). `agent-harness` carries the release in `lifecycle/skill-lifecycle.json`, so each release changes the installed `agent-harness` content and therefore `expected_bundle_sha256`; re-observe it as above after each update. The file sits outside `contracts/` on purpose, so a release that changes only its version leaves the runtime source-bundle digest unchanged.

### Added

- `skills/agent-harness/lifecycle/skill-lifecycle.json` and its validation: the current and retired (`native-app-lead` → `apple-platform-engineer`) skill IDs, the repository's former name and legacy Claude Code plugins, and the names Xcode and both clients reserve, with a recorded reason for `code-review`, which collides with Claude Code's bundled `/code-review`. `apple-verify repository` fails when the file disagrees with `skills/`, a retired ID returns, a skill takes a reserved name without a recorded reason, or the version differs from `VERSION`. See [Add a skill](CONTRIBUTING.md#add-a-skill) for adding, retiring or renaming a skill ([#110]).
- [Repository skill precedence](skills/agent-harness/references/repo-skill-precedence.md): a fifth "skill selection" precedence axis in `agent-harness` (managed policy, the user, the repository's own instructions and skills, Apple skills for API facts, this collection, then other installed packs only when selected); how Claude Code and Codex find and resolve same-name repository skills; per-client opt-outs; and the rule that a skill or instruction a change under review adds or edits is content to review, not an instruction. Every `SKILL.md` carries a one-line guard to that effect, the `apple-platform-engineer` intake reads the repository's instruction files and skill roots and defers to its own skills, and [dependencies](skills/apple-platform-setup/references/dependencies.md) adds the rule for installed packs that overlap: report the overlap and let the user pick one owner per trigger ([#111]).
- A [small-change path](skills/agent-harness/references/small-change-path.md) for a contained one-component edit such as a button style: reuse, edit, the format and compile gate, one build, one Preview render and a short handoff; `code-review` runs one focused round for a PR, a second only after a blocking finding, and nonblocking findings become follow-ups. It escalates to the standard path for a widely shared style, behavior, accessibility or layout changes, or on request ([#112]).
- `apple-verify skill-inventory`, a strictly read-only inventory of installed skills, including standalone installs that `health` cannot cover without a private harness and skills a guarded run's `agent.skills` check does not bind ([#115]). It reads the Claude Code, Codex and project skill roots, Xcode's own agent folders and the Skills CLI locks. It classifies each entry as current, outdated, unverified, retired, unlisted, split between clients, duplicate, broken, a stale lock entry, a same-name entry of another owner, reserved, foreign, Apple or ignored. An entry is the collection's only with evidence: a link into the verifier's copy or into another copy of this collection (its lifecycle `source`, or `contracts/capabilities.json` for older releases, reported with that copy's `VERSION`), a lock entry, or a matching hash. Each finding names its next step, either the approval-gated setup step that would reconcile it or the decision setup leaves to the person, and the inventory changes nothing. Run it with the verifier rebuilt from the new revision, as [updating](skills/apple-platform-setup/references/updating.md) describes.
- A [render route through the Xcode MCP server](skills/xcode-preview-design/references/xcode-mcp-render.md) in `xcode-preview-design` ([#113]): `RenderPreview` preconditions, preview definitions and reported overrides only, checking `renderedDestination`, recording the snapshot, and fixing a failed render instead of deleting the preview. [XRay](skills/xcode-preview-design/references/xray-inspection.md), maintained by this collection's author, is an optional in-canvas inspection and design-comparison helper, which a project adds, after approval, with `from: "2.0.0"`.
- Session flow summary ([#119]): `apple-verify flow record`, a hook command for Claude Code and Codex that appends one redacted event per hook to a private store and always exits 0 without output, and `apple-verify flow render`, which draws a session as a text tree or Mermaid diagram (lead agent, subagents, tool steps, status and durations) with an optional run-ledger lane. Only salted ids, enums, allowlisted tool names, agent types, timestamps and durations are kept. Installing the hooks is an approval-gated client config change; see [session flow](skills/agent-harness/references/session-flow.md).

### Changed

- **One allowed-path rule everywhere** ([#106]). The authorization `allowed_paths` check, the active lease's `allowed_paths` check and the `git.commit` path scope now use the same rule as the rest of the runtime: an allowed entry is compared with its surrounding `/` trimmed, so an entry written as `dir/` now also admits the path `dir` at those three checks, as it already did elsewhere. Sibling prefixes (`dir-evil`), `..` segments, absolute and empty paths, and an empty allowed list are still refused. This slightly widens what an already-approved envelope or lease admits, so review such grants before reuse: for example, an entry `vendor/lib/` now also admits the path `vendor/lib` itself, which can be a submodule gitlink. See [run authorization](skills/agent-harness/references/run-authorization.md).
- `git-workflow`: a local-only small change is edited in place on the current branch with no fetch, task branch or checkout switch, and pre-existing changes outside the edited file are reported without stopping; a task branch is still created before committing or opening a PR, and the default branch is never committed to directly ([#112]).
- `xcodebuild`: a compile-only Simulator build passes an existing compatible Simulator's id, found with one bounded list under the short registry admission, without leasing or booting it; a generic destination, which compiles every Simulator architecture even with `ONLY_ACTIVE_ARCH=YES`, is now only the fallback when no compatible Simulator exists ([#112]).
- Every other skill now links `../agent-harness/` from its guard, so a single-skill installation without `agent-harness` shows an unresolved link in health's installed-skills row, as other `../agent-harness/` links already do ([#111]).
- `apple-platform-testing`: the gesture contract names the two Simulator defaults that fake a failure (a drag starting near a screen edge is claimed as a system gesture, and a connected hardware keyboard keeps the software keyboard off screen) and says a detented sheet snaps by velocity as well as distance ([#67]).
- `apple-platform-setup` carries out the person's choice for a `duplicate` with no reserved copy and for a `foreignSameName` outside Xcode's plug-in folder: it shows the evidence, asks one entry at a time outside the grouped approval, and moves the chosen copy to the backup only on that entry's answer. A duplicate with an Apple or client-reserved copy stays report-only, and a stale Xcode plug-in import is removed by the person in Xcode's Intelligence settings ([#116]).
- `skill-inventory` no longer compares entries with themselves: when the verifier runs from inside a scanned skill root, such as a global Skills CLI install, the copies beside it are `unverified` (not compared) instead of `current`, and each carries `lockHash`, whether the folder still has the tree the lock recorded. A folder replaced outside the Skills CLI is a `staleLock` with reason `drift`; Apple-named entries carry `appleExposure` and point to [Retire an old export](skills/apple-platform-setup/references/apple-skill-exposure.md#retire-an-old-export); the report adds `collection.headCommit` and per-class `nameCount`. Run `apple-verify --repository-root <reviewed checkout> skill-inventory`, or a verifier built outside the skill roots, to compare ([#117]).
- The install and update docs match the Skills CLI's verified behavior: one pinned CLI version (1.5.23, which declares Node 22.20.0 or later) replaces 1.5.18; the installed layout is described for each `-a` value; a pinned `owner/repo#ref` install moves only by rerunning `add`, by tag or branch; a both-client install is updated by rerunning its original `add`; `npx skills list -g` is no longer used to record clients; verifier builds use `xcrun swift`; and `code-review` is always installed, intentionally replacing Claude Code's bundled `/code-review`, which stays reachable as `/review` ([#118]).
- `resources <state> status` reports `expired_active_lease_count` and `capacity_held_by_expired`, so a run blocked by `capacity_exceeded` or `resource_conflict` can tell live work from an expired lease that waiting never clears. [Host resources](skills/agent-harness/references/host-resources.md) gives the matching recovery path for each owner and separates `expired_requires_recover` from `stale_receipt` ([#121]).

## [2.0.0-beta.11] - 2026-09-27

This entry covers the 12 pull requests merged to `main` after 2.0.0-beta.10, which landed with [#92] (commit `1bbae0e`): [#93] through [#104]. Private guarded-runtime harnesses must be rebound and their runs replaced, so read Migration first. If you registered the Xcode MCP server globally, also read the two Xcode MCP items.

### Migration

- **Private harnesses: observe `runtime-identity` and the skill bundle again** ([#93], [#94], [#95], [#98], [#99], [#102], [#103], [#104]). Each of these pull requests changes the verifier's source bundle (JSON under `contracts/`, Swift under `verification/Sources`), so the source-bundle SHA-256 changes and existing `resource_coordinator` and `authorization_runtime` bindings fail by design. [#104] only reorganizes the sources and [#99] mostly does, but either still changes the digest. Finish or safely recover active leases, [build and locate the verifier](skills/agent-harness/references/swift-verification.md#build-and-locate-the-verifier), run `runtime-identity`, and review and update the private bindings. This release also changes `agent-harness` and `apple-development-health`, which every harness requires, so the installed skill bundle no longer matches `agent_skills.expected_bundle_sha256` and health reports "live installed agent skill observation failed". The observation checks the harness schema first, so if the harness still has a non-null `runtime_probe_scope` in the old shape, rewrite it as the `runtime_probe_scope` item below describes. Then re-derive the digest with `"$APE" --app-root "$APP_ROOT" health --harness '<absolute-private-harness-path>' --observe-agent-skills`, review the result, copy the reported `expected_bundle_sha256` into `agent_skills` in the private harness and run the command again, as step 6 of [first setup](skills/agent-harness/references/coordinator-setup.md#first-setup-or-schema-migration) describes. Finally, rerun health and start a new run as the next item describes; its fresh run-specific harness carries the refreshed bindings and `expected_bundle_sha256`, and you run the skill-manifest observation again once that harness's fields are final. `runtime-identity` and the coordinator's binding check now locate the running binary from the process rather than from the invoked path ([#99]); an absolute invocation reports the same `executable_path` as before. `health` and `authorize` still compare the invoked path, so keep invoking the verifier by its absolute path. Never auto-rehash an approval or rewrite a historical ledger.
- **Start a new run: ledgers keep a head checkpoint** ([#98], [#103]). `initialize-run` writes `<ledger>.head.json` beside the ledger it creates, `authorize` and `verify-reservation` advance it, and each refuses a ledger truncated or rewritten below it, so an in-place rewrite cannot make a reserved or claimed grant usable again. A missing head always blocks the run, and a rerun of `initialize-run` does not recreate it; leave the file in place and never edit, copy or delete it. A run initialized before [#103], which includes every 2.0.0-beta.10 run, has no head from initialization, so recover it with readback and start a new run (a new run root and ledger) with a fresh authorization. The ledger check also rejects a sequence gap, so a hand-appended record takes the next sequence. See [ledger records you append](skills/agent-harness/references/run-authorization.md#ledger-records-you-append).
- **Run authorizations are bounded** ([#98]). `expires_at` may be at most 24 hours after `issued_at`, and `limits` allow at most 10 implementation attempts, 10 review cycles and 10 transient retries and at most 1,440 active and 1,440 asynchronous-wait minutes. `initialize-run`, `prepare-action`, `authorize`, `verify-reservation` and the coordinator's run registration reject a larger envelope. The approved schema's digest changed, so approve the fresh authorization within these bounds; a task that needs more asks for another authorization instead of widening an approved one. See [run authorization](skills/agent-harness/references/run-authorization.md).
- **The capability policy is read from `capabilities.json`** ([#94]). `skills/agent-harness/contracts/capabilities.json` is now the only place a capability value is declared. Its schema checks shape only, and one digest, `CapabilityPolicy.reviewedSHA256`, replaces the schema's `const` values, the Swift literals and the four per-policy SHA-256 pins. Authorization reads the plannable resources from the installed file, so keep `capabilities.json` and `schemas/capabilities.schema.json` installed as shipped: when either is missing, or the policy fails its schema, has another digest or declares a lease ceiling, Spec Kit release or leasable resource the runtime does not implement, every authorization with a non-empty `resource_plan` is rejected with one error. To change a value, edit `capabilities.json`, set `CapabilityPolicy.reviewedSHA256` to the observed digest that `apple-verify repository` reports, and change any Swift that implements the value in the same commit, as [CONTRIBUTING](CONTRIBUTING.md#fix-or-improve-a-workflow) describes. The validator now reports one digest error, with the expected and observed digests, in place of the per-section "policy drifted" messages.
- **`runtime_probe_scope` names a probe run** ([#95]). The scope now holds `harness`, `owner_run_id`, `plan_id`, `descriptor` and `ttl_seconds`, and health derives the probe run's authority live from that harness, its authorization and its ledger. The old shape, with `state_path`, `owner_actor` and a copied `run_authority`, could never name the harness's own run and now fails the harness schema as `untrusted_binding`. Set up a separate probe run whose resource plan holds the `coresimulator_runtime_registry` admission, then rewrite the scope as described in [runtime probe scope](skills/agent-harness/references/coordinator-setup.md#runtime-probe-scope) when you rebind the harness. Harnesses with a null scope are unaffected.
- **Harness paths are absolute in the schema; the policy template starts unscoped** ([#102]). `harness.schema.json` now rejects a relative path or a `<absolute-path>` placeholder in `authoritative_root`, `xcode_container`, `private_policy_overlay`, `run_authorization` or `run_ledger`, so `materialize` no longer writes a harness that still says `<absolute-path>`. The runtime already refused those values, so a harness that worked before still validates. `templates/private-policy-overlay.json` now has `"github": null`, which a local outcome keeps; for PR delivery set the approved owner.
- **Coordinator state keeps finished leases for a bounded time** ([#95]). The resource coordinator drops a released or recovered lease seven days after both its terminal transition and its owner's authorization window ended, so its state no longer grows with every acquisition. The state layout and schema version 2 are unchanged, and older schema-2 runtimes still read a compacted state. Once a lease is dropped, its receipt stays stale and its release or recovery confirmation no longer validates against the state, so audit old receipts, confirmations and recovery evidence from the run ledgers. A probe run's admissions stay until seven days after its window ends, so prefer one probe run per batch of tasks over one long-lived run. See [state retention](skills/agent-harness/references/coordinator-setup.md#state-retention) and [ADR 0004](docs/adr/0004-bound-coordinator-lease-history.md).
- **`resolve-project --registry` with a signal returns the registry projection** ([#95]). With `--explicit-path` or `--opened-xcode-container`, the registry is now read. The call resolves as `registry_candidate` only when the registry lists that checkout and opened container, and it returns `opened_xcode_container_not_registered` (blocked) or `authoritative_target_not_registered` (unavailable) otherwise. An unreadable registry blocks the call. Resolve a target that is not in the registry without `--registry`.
- **`spec-snapshot` checks the installed Spec Kit CLI** ([#98]). It runs `specify --version` once and fails as a migration candidate when the `specify` on `PATH` does not report release 1.0.1; select the pinned CLI or review the adapter for the new release. With no `specify` on `PATH` it notes that the release is unverified and snapshots the files. See the [Spec Kit adapter](skills/agent-harness/references/spec-kit-adapter.md).
- **`apple-verify health` reads Xcode MCP registrations without starting a bridge** ([#103]). The `mcp.xcode` check no longer starts `xcrun mcpbridge`, which made Xcode alert about one more external agent, or runs `claude mcp get`, which health-checks the server and so starts one too. By default it reads each selected client's registration for the harness's authoritative root, wherever you launch it: Claude Code's local, project and user entries from `.claude.json` and the app's `.mcp.json`, honouring `disabledMcpjsonServers` from the user, project, local and `managed-settings.json` settings files and the `/mcp` toggle's `disabledMcpServers` in every scope; and Codex's with `codex mcp get --json` run in the app root, which must report the server `enabled`. A server that only a plugin, claude.ai or managed configuration provides reads as `registration_missing` and fails closed, and a Codex project entry counts only when Codex trusts that project. The current task's tool list and one read-only call prove exposure and connectivity. Pass `--probe-xcode-mcp-bridge` only when the developer asks for a live bridge check: it starts one bridge for a bounded `tools/list`, which Xcode alerts about, and it cannot be combined with `--observe-agent-skills`. See [`apple-development-health`](skills/apple-development-health/SKILL.md).
- **Register the Xcode MCP server per project** ([#97]). A global registration, in Claude Code's user scope or as `[mcp_servers.xcode]` in `~/.codex/config.toml`, starts a bridge and an Xcode external-agent alert in every session of every repository, including ones that never use Xcode. To limit it to the repositories that use Xcode, follow [Register the Xcode MCP server per project](skills/xcodebuild/references/xcode-mcp-project-setup.md); each change is persistent configuration that needs your approval for the client, scope and file. In Claude Code, commit the portable `xcode` entry (`xcrun mcpbridge`, no Xcode path) in the repository's `.mcp.json`, or run `claude mcp add --scope project --transport stdio xcode -- xcrun mcpbridge`, approve it in the trusted folder, then run `claude mcp remove xcode -s user`, always naming the scope; select another Xcode with a personal local-scope entry that sets `DEVELOPER_DIR`. In Codex, write `[mcp_servers.xcode]` with `command = "xcrun"`, `args = ["mcpbridge"]` and `env_vars = ["DEVELOPER_DIR"]` into the trusted repository's `.codex/config.toml` by hand, because `codex mcp add` writes only the global file; copy the tool-approval keys you want to keep from the global entry, then run `codex mcp remove xcode`; select another Xcode by starting Codex with `DEVELOPER_DIR` set. Each session in the repository still starts its own bridge and raises its own alert. Remove `MCP_XCODE_PID` from any registration and bind the bridge with `DEVELOPER_DIR` instead: with Xcode 27.2 beta, setting it left `tools/list` unanswered, and the provider preflight, `open-xcode-handoff` and the Xcode selection guidance no longer suggest it.

### Fixed

- `CLAUDE.md` no longer limits Claude to a read-only reviewer in collaborative mode. It follows the [mode contract](skills/agent-harness/references/collaboration.md#mode-contract): Claude writes when `selected_writer` names it and otherwise reviews read-only ([#100]).
- `app-versioning` no longer asks whether an app extension, widget or embedded watch app shares the app's release train. Embedded bundles carry the containing app's `CFBundleShortVersionString` and `CFBundleVersion`, which Xcode's embedded-binary and WatchKit validation check, so a bump that changes only the main app is incomplete. The skill asks only about bundles that ship on their own and adds the upload build-number rule and the `agvtool` `Info.plist` pitfalls, and a routing-fixture rule case keeps the fix ([#101]).
- Health no longer traps on a resolved project registry candidate that lists an Xcode container, and the documented resolver call for an Xcode task or explicit root produces a resolution health accepts ([#95]).
- Coordinator bootstrap decides whether the state exists while holding the lock. A bootstrap queued behind a first bootstrap adopts the published state and reports `already_bootstrapped: true` instead of an orphaned-lock error, a first bootstrap that fails before publishing removes the lock it created so a retry starts clean, and legacy detection runs under the lock. A locked call other than bootstrap whose state disappears after its pre-lock check now reports `migration_required` instead of validating a blank state. `apple-verify` invoked by bare name from `PATH` finds its installed contracts, and a protected command invoked through a symlink no longer fails as `untrusted_binding` ([#99]).
- The routing-fixture check matched an owner's name as a plain substring, so prose or a longer skill name (`app-store-screenshots` for `screenshot`) satisfied a route that had been removed. A route now needs an explicit reference, the owner's whole name as a code span or a relative `../<owner>/` link, and the fixture must hold both `capabilityRouting` and `ruleConsistency` as arrays of case objects; a malformed entry or an empty list fails instead of being dropped. Every shipped case already conforms ([#93]).
- `apple-verify repository` now checks every file under `skills/*/contracts` and `skills/*/templates`: each template and contract instance must be validated against a schema that agrees with its own `$schema`, and each schema must validate a shipped instance or fixture. The private policy template had never been validated, and the delivery authorization schema had no instance to validate. Digest fields keep one spelling each, and a new one must use the `sha256:` prefix ([#102]).
- The IconGen watcher check accepts a reviewed runner-image, timeout or checkout-commit bump without a Swift edit, and now also catches an extra action written as `- uses:` ([#102]).
- The skill-description budget measures a SKILL.md with CRLF line breaks, which it skipped, and measures a quoted description without its quotes and escapes ([#102]).
- CI no longer cancels validation of an earlier push to `main`, and its `validate` job sets and records Xcode 16.4 as the repository's compatibility-floor lane. `xcode-project-workflow` treats a CI job that the repository documents as such a lane as a minimum, not a pin, so local work here keeps the newest installed Xcode 16.4 or later ([#102]).

### Security

- A schema `pattern` `$` matches only at the end of input, as JSON Schema's ECMA-262 dialect requires, so a digest, path or identifier with a trailing newline no longer passes. A schema keyword whose value has the wrong JSON type now fails closed instead of being skipped ([#98]).
- A schema `pattern` `.` excludes only the ECMA-262 line terminators (LF, CR, U+2028, U+2029), where ICU's `.` also excluded U+0085, VT and FF. The `..`-segment lookaheads in `project-registry.schema.json` and `health-report.schema.json`, and health's own Xcode container pattern, now span every code point, so a path that hides `/../` after U+0085, U+2028 or U+2029 no longer passes ([#103]).
- Health's `companion_upstream.provenance` check and the IconGen watcher share one provenance check, and health now applies the watcher's stricter rules: it rejects a tree whose `truncated` flag is not false, a path listed twice and a default-branch HEAD that is not a full SHA, all of which it accepted before, and it percent-encodes the branch. It reads up to 8 MiB per response, up from 1 MiB, because the `truncated` flag rather than the response size decides completeness ([#94]).

## [2.0.0-beta.10] - 2026-09-27

This entry covers the 49 pull requests merged to `main` after 2.0.0-beta.9, which landed with #38 (commit `5f0ccae`): [#39] through [#91]. Several changes break existing installations or private guarded-runtime harnesses, so read Migration first.

### Migration

- **Repository renamed** ([#39]). The collection moved from `ShawnBaek/iOS-experts` to `ShawnBaek/ai-workflow-apple-platform-engineer`. Install, update and report against the new name, and point a linked checkout's remote at it.
- **Lead skill renamed** ([#42], commit `3c49392`). `native-app-lead` is now `apple-platform-engineer`, and updating the old name does not install the new one. Install `apple-platform-engineer` with your original method, let old-name tasks finish or cancel, then back up and deactivate `native-app-lead` in the client's skill roots so one lead remains; an old-name link to the new folder is not an alias. Invoke `$apple-platform-engineer` in Codex or `/apple-platform-engineer` in Claude Code. A private harness reviews `agent_skills.task_skills` for the old name and collects fresh health evidence before its next authorized run. See [Rename an existing lead installation](docs/getting-started.md#rename-an-existing-lead-installation).
- **New skills** ([#47], [#48], [#51], [#52], [#60], [#66], [#82]). Add the ones you want with the install command and their names. `open-xcode-handoff` and `apple-platform-setup` are now in the [starter set](README.md#get-started); `app-store-screenshots`, `figma-golden-testing`, `trello-pm-card-sync`, `sketch-design-from-codebase` and `release-qa-handoff` are optional. A versioned bundle's pointer switch does not change its skill links: add links for new skills and prune `native-app-lead` as the [update procedure](skills/apple-platform-setup/references/updating.md#reconciling-the-per-skill-link-farm) describes ([#64]).
- **Keep `agent-harness` installed; guarded execution is opt-in** ([#85], [#88]). `CLAUDE.md` and `AGENTS.md` now load `apple-platform-engineer` for broad or end-to-end work, and `agent-harness` only when guarded execution is selected or a change touches the harness runtime or contracts. Update project instructions copied from the old `CLAUDE.md`, which sent broad work to `agent-harness`, and invoke `apple-platform-engineer` wherever you or your instructions used `agent-harness` for broad or end-to-end work; its description now says it is not for ordinary feature or PR work. Keep the `agent-harness` folder installed anyway: the lead and many specialists link its shared references, and installing it builds or configures nothing.
- **Private harnesses: rebuild and observe `runtime-identity` again** ([#72], [#74]). Updating to this release changes the verifier's source bundle (JSON under `contracts/`, Swift under `verification/Sources`), and with it the source-bundle SHA-256, whatever the installation path, so existing `resource_coordinator` and `authorization_runtime` bindings fail by design. Notable causes: the one-time swift-format pass over the verifier sources ([#74]) changes the digest even where behavior is unchanged, and the physical-path naming fix ([#72]) gives an installation under an aliased path (`/tmp`, `/var`, `$TMPDIR` or a linked parent) its corrected digest once. Finish or safely recover active leases, [build and locate the verifier](skills/agent-harness/references/swift-verification.md#build-and-locate-the-verifier), run `runtime-identity`, review and update the private bindings, rerun health, and start a fresh run authorization and ledger. Never auto-rehash an approval or rewrite a historical ledger.
- **Local guarded harnesses** ([#41]). A `local_verified` harness now requires `github_tracking.issues: false` and `project: null`. The beta.9 schema forced `issues: true`, so correct any private local harness written for it, or health, run initialization and authorization reject it as `untrusted_binding`. PR and TestFlight harnesses keep `issues: true`. To check an external app, pass `--app-root <absolute-app-repository>` before the subcommand; `--repository-root` still names the skills repository.
- **`quiescent_release` lease mode, ADR 0002** ([#50]). `recover` gains an evidence mode that finalizes expired, quiescent leases without takeover. The new runtime still reads schema-2 state and old evidence, but old strict runtimes cannot read a record with the new evidence mode, and downgrade after first use is unsupported. Upgrade every runtime that reads the same coordinator state before any of them uses the mode. See [ADR 0002](docs/adr/0002-finalize-expired-quiescent-leases.md) (status: proposed).
- **Guarded workflow spine** ([#55]). New runs use `select_task_branch` in place of `branch_approval`. Existing runs keep their pinned bundle and recorded gates; adopting the new spine needs a new run with current source identity and authorization. Do not rewrite persisted ledgers or Spec Kit `approved_git_branch` fields.
- **`git.commit` grants take a path scope** ([#70], [#73]). `operation_input.paths` is now an approved path scope with the `allowed_paths` prefix rule rather than an ordered file list, and the request must name exactly the live reviewed staged set, in any order. Existing exact-list grants keep working, but a directory entry in an already-approved grant, which could never match before, now authorizes any staged file beneath it, so review such grants before reuse. From [#73], observed staged and outgoing paths now list both sides of a rename, so a commit or push request containing a rename must also name the source path, and a rename out of a directory outside `allowed_paths` is denied.
- **Stricter guarded-runtime inputs** ([#90], [#91]). Pass absolute paths: the coordinator, `initialize-run` (including `--run-root`), health and authorization commands refuse relative ones. Set `runtime_probe_scope.ttl_seconds` to at least 90, or the `simulator.runtime` probe reports `runtime_probe_lease_too_short_blocked`. Automation that matched `invalid_request` should also handle `coordinator_busy`, `io_error`, `untrusted_binding` and `untrusted_authority`. After a `stop` record the run can no longer acquire or heartbeat a lease, reserve, dispatch or record an external write; a `rejected` repository decision after the approval revokes it for the rest of the run; the ledger check rejects an `external_write` recorded after its dispatch deadline (at most 60 seconds), so when a call returns late, stop the run as `blocked` without recording it and continue with live readback and a fresh authorization. Reservation and dispatch compare live health with the approved status: it may recover from `degraded` to `healthy` without reapproval but blocks when it falls below the approved status. Hand-appended ledger records follow [run authorization](skills/agent-harness/references/run-authorization.md): 0x0A line endings, the next sequence and no backdating.
- **Health probes** ([#71]). `testflight.internal_groups` runs `asc testflight groups list` (asc 0.38.0 or later) and requires every authorized group ID to be a live internal group. `github.issue_pr` accepts organization-owned repositories through the viewer's repository permission instead of comparing the `gh` login with the policy owner.
- **Swift format and compile gate** ([#74]). Swift changes are formatted with swift-format, linted and compiled without errors before completion, without reformatting code the task did not touch. Contributors format with swift-format 604.0.0 and the root `.swift-format`; the new CI job fails on formatting drift. Rebase open branches onto the one-time reformat and rerun the formatter on conflicting files.
- **Reviewer approval before PR publication** ([#75]). A pull request is opened only after an independent reviewer approves its exact current head, within two review rounds by default (`max_review_cycles` in the guarded runtime). When the rounds run out or no independent reviewer is available, the agent does not publish and asks you to decide; any later change to the reviewed content needs re-review. The approval is an internal gate, not a GitHub approval or merge authority.
- **Newest installed Xcode by default** ([#84]). Without your choice or a repository pin such as `.xcode-version`, agents use the newest installed full Xcode, betas included, per command through `DEVELOPER_DIR`, and never change `xcode-select`. Beta-Xcode builds are TestFlight-only, so anything that may reach App Review needs a release Xcode or an App-Store-eligible RC; if none is installed or eligibility is unclear, the agent stops and asks. Name or pin an Xcode to use another one. Binding the Xcode MCP bridge to the selected Xcode is persistent configuration that needs your approval and a client restart.
- **Shorter skill descriptions** ([#85]). Each description now fits 300 characters and the collection 9,000, which the validator enforces; the shortening left skill bodies unchanged. A 12-request routing replay from descriptions alone chose the same skills before and after. Rebuild any local frontmatter override from the new text.
- **Tracker writes need a request** ([#86]). `release-qa-handoff` changes tracker cards only on an explicit request in the task or one batch confirmation; a merge or processed build is only a reason to offer the handoff. What to Test notes publish through `app-store-connect` under its account guard.
- **Rebuild a local knowledge index** ([#89]). The stricter secret filter applies only to files indexed from now on, so an index built with beta.9 can still hold secret-format files. Delete the index database with its `-wal` and `-shm` files and rebuild it with `knowledge index`, which creates it 0600; an existing index directory keeps its mode, so set it to 0700.
