# Competitors, references and design direction

Use this intake for new UX/UI, an app website, an icon concept or a substantial
visual/interaction redesign when reference products or style preferences would
change the result. Reuse the accepted task brief, brand system and previous
answers. A precise layout fix, faithful implementation of an approved Figma
frame, icon export or packaging task does not need a competitor survey.

## Ask about the experience before choosing a style

Combine missing questions into the existing intake round:

1. **Which competing or reference apps/services should we study?** Which
   feature or flow matters, and what do you like or dislike about it? Ask for a
   link or exact product/platform only when the name or relevant experience is
   ambiguous. Functional competitors and visual references can be different.
2. **What style do you prefer?** For example, native/minimal, playful,
   editorial or dense/professional. Which brand colors, typography, information
   density or motion preferences should we preserve or avoid?

For a new screen with no accepted design direction, ask these missing questions
in the next response before choosing the presentation. Omitted preferences are
not the same as "no preference" or permission to choose on the user's behalf.
Independent project inspection can continue while the answer is pending.

Ask only for missing information that affects the work. An explicit "no
reference", "keep our existing style" or "you choose" is an answer. When the
user delegates the choice, propose a small direction grounded in their audience,
existing product and Apple guidance, state the assumption, and proceed with a
reversible draft. Do not invent a preference or repeatedly ask the same question.
Keep work that depends on an unresolved material choice pending; continue
independent inspection or research while an answer is outstanding.

## Research the selected app or service

Inspect the relevant feature and platform using current official product pages,
help documentation, demos, App Store screenshots or user-supplied references.
Use read-only public evidence where practical and stop when it answers the
design question. A small screen change needs a few relevant observations, not a
market report or a full competitor matrix.

For each useful finding, retain its source URL or artifact, date/version when
available, and the observed flow or visual pattern. Separate direct observation
from inference and your recommendation; screenshots do not prove hidden states,
interaction behavior or performance. State access limits instead of inventing
unseen screens or claiming to have tested an app you only read about.

Explain which patterns to adopt, adapt or avoid and how they serve the user's
feature and preferred style. Check the proposal against the project's minimum
OS, current Apple HIG, accessibility and relevant performance constraints.
The user's approved design source and explicit requirements guide the result;
surface a material conflict before changing them. Competitor references do not
silently expand the feature scope or grant permission to change a Figma file.

## Carry one direction into implementation and review

Add only the useful findings to the existing task brief: selected references,
likes/dislikes, preferred style, source-backed observations, proposed choices
and observable acceptance criteria. Pass that same brief to UI, Preview, Figma,
website, icon and review work so specialists do not repeat the intake or invent
different preferences. Update affected decisions when the user changes direction.

Make a small Preview or appropriate design draft before dependent app logic
when the visual direction needs validation. Review both the intended experience
and relevant evidence, such as layout alignment, a motion recording or a focused
interaction check. Research supports the design decision; the implemented
feature still needs its own verification.
