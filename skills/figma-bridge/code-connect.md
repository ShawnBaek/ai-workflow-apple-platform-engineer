# Code Connect for SwiftUI

Code Connect is the durable link between a Figma component and the real SwiftUI type that implements it. Once wired, Dev Mode and the Figma MCP server point at the engineer's actual component instead of autogenerated code. It is available on Figma's Organization and Enterprise plans with a Dev or Full seat.

Write mappings from Figma's current docs, not from memory. In 2026 the CLI moved to template files, and SwiftUI parser examples no longer publish with the current CLI.

## Two routes (they can coexist)

| Route | Where mappings live | What Dev Mode and MCP get | Best for |
|-------|---------------------|---------------------------|----------|
| **Code Connect UI** | Stored in Figma, not in the repo. Dev Mode → file-name menu → Library → *Connect components to code*. Nothing to install | The component's source path and name, plus optional MCP instructions. There is no code snippet in Inspect | Designers and engineers mapping from Figma, or one component mapped to several frameworks |
| **Code Connect CLI** | In the repo: `figma.config.json` plus one template file per component, published from the terminal or CI | A dynamic code snippet that follows the instance's properties | Design-system components whose snippet must track Figma variants and props |

Connecting a GitHub repository to the UI is optional. It adds path autocomplete and codebase context. Only one repository can be linked to each library file, the connection needs the file owner or an organization admin, and GitHub Enterprise Server is not supported. You can use both routes together. Connections created with the CLI appear in the UI but can only be edited through the CLI, and `publish --force` overwrites a conflicting UI mapping.

Comparison reference: https://developers.figma.com/docs/code-connect/comparing-cc/

## Parsers vs template files

Figma has retired the framework-specific parsers, including the SwiftUI one. Parsers stopped receiving updates on 17 August 2026, and template files are now the only format Figma maintains. Since CLI v2.0.0, a parser project can still run `figma connect migrate` and `figma connect unpublish`, but `publish`, `preview` and `parse` exit and ask you to migrate. `create` behaves differently, as Route A explains. So:

- **New mappings:** write template files (Route A).
- **An existing repo with SwiftUI `FigmaConnect` structs:** migrate before you change any mapping. Follow Figma's migration guide (https://developers.figma.com/docs/code-connect/templates-migration-guide/) and keep these points in mind:
  - Run `npx figma connect migrate --outDir CodeConnect` from the directory that holds the current `figma.config.json`. Without `--outDir`, templates are written beside the parser files, usually inside a build target (see *Location* below). Treat the output as a starting point to review.
  - By default (`--batch auto`), a source file with 10 or more connections, such as an icon catalog, can become a `.figma.batch.ts` template plus a `.figma.batch.json` list. Only the JSON file leads the CLI to that batch. Pass `--batch none` to always write regular template files instead.
  - Unless one already exists there, the CLI also writes a `figma.config.json` into `CodeConnect/`, and its `include` gains `**/*.figma.batch.json` when batches were written. The CLI reads only the config in the directory it runs from and resolves `include` globs from there. Copy that file's `label`, `language` and `include` into the root config, prefixing each glob with `CodeConnect/` (for example `CodeConnect/**/*.figma.batch.json`), then delete it. Remove the Swift-only keys (`xcodeprojPath`, `swiftPackagePath`, `sourcePackagesPath`, `importMapping`) and any `parser` key from the root config.
  - Do not pass `--delete`. It deletes every source file whose connections all migrated, which for SwiftUI is the `.swift` file holding the struct and is often the view itself. After the templates are published, remove the structs and any `#Preview` that uses them by hand. Remove the `Figma` package product only when nothing imports `Figma`.
  - Publishing needs the same authorization as in Route A. If you first rehearse under a temporary label such as `TEST`, as the guide suggests, that config's `include` needs the batch glob too.
- **Keeping the parser for now:** pin CLI v1 (`npm install --save-dev @figma/code-connect@1`), which no longer receives parser updates. That adds a `package.json` and `node_modules/`. Add `node_modules/` to `.gitignore` and keep both outside any synchronized folder. The CLI would otherwise detect the `package.json` as a web project, so set `"parser": "swift"` in the config. Never start new parser files.

## Route A — CLI with template files

Install the CLI once per machine (Node.js 18+):

```bash
npm install --global @figma/code-connect@latest
```

The CLI authenticates with a personal access token that has the *Code Connect* scope set to Write and *File content* set to Read. Pass the token through `FIGMA_ACCESS_TOKEN` (or `--token`) from the environment. Never put it in `figma.config.json` or the repo.

Create `figma.config.json` in the project root, next to the `.xcodeproj` or `Package.swift`:

```json
{
  "codeConnect": {
    "include": ["CodeConnect/**/*.figma.ts"],
    "label": "SwiftUI",
    "language": "swift"
  }
}
```

- **`include`:** may match only template files and `.figma.batch.json` files, not the `.figma.batch.ts` templates those JSON files name. Unless the config sets `parser`, the CLI detects one by walking up from the working directory. In each directory a `package.json` (a web parser) is checked before an `.xcodeproj` or `Package.swift` (Swift). With a parser detected, v2 exits if `include` matches no files or any file that is neither.
- **`language`:** controls syntax highlighting.
- **`label`:** names the snippet in Dev Mode and is the value an MCP client filters on. Figma's quickstart suggests `Swift` for a new SwiftUI repo, while the legacy SwiftUI parser published under `SwiftUI`. Both are valid, so keep whatever label the repo already uses.
- **Location:** Figma's examples keep template files beside the component. In an Xcode project, choose a directory that no synchronized (buildable) folder or XcodeGen source glob covers, so the build never sees them. `.figma.js` also works if the repo has no TypeScript.
- **Batch files:** for many components that share one code shape, such as an icon set, Figma recommends one `.figma.batch.ts` template plus a `.figma.batch.json` list instead of a file per component. Add `CodeConnect/**/*.figma.batch.json` to `include`, which reaches the template through the JSON file. See https://developers.figma.com/docs/code-connect/batch-files/.

`npx figma connect create "<node URL>" --outDir CodeConnect` is documented to generate a boilerplate `.figma.ts` for one component. The v2.0.1 source, however, sends `create` to a legacy parser whenever it detects one: Swift from the `.xcodeproj` or `Package.swift`, or a web parser (HTML, or React if it lists `react`) from a `package.json`. Judge the result by its content, not its extension. It is a template only if it opens with the `// url=` metadata comment and imports `figma` from `'figma'` (either quote style), like the example below. The HTML parser also writes a `.figma.ts` file, but that file imports from `@figma/code-connect/html` and calls `figma.connect(...)`. The React parser writes a similar `.figma.tsx`, and the Swift parser writes a `FigmaConnect` struct to a `.figma.swift` file or fails. In any of those cases, delete any generated file so `include` never matches it, then write the template yourself or with Figma's `figma-code-connect` skill.

A template file begins with its metadata comments and default-exports the snippet. Figma evaluates it for each selected instance:

```ts
// url=https://www.figma.com/design/<fileKey>/<fileName>?node-id=12-34
// source=Sources/DesignSystem/AppButton.swift
// component=AppButton
import figma from 'figma'

const instance = figma.selectedInstance

// Escape the text for a Swift string literal
const title = instance
  .getString('Label')
  .replaceAll('\\', '\\\\')
  .replaceAll('"', '\\"')
  .replaceAll('\n', '\\n')
  .replaceAll('\r', '\\r')
const style = instance.getEnum('Variant', {
  Primary: '.primary',
  Secondary: '.secondary',
})
const disabled = instance.getBoolean('Disabled')

export default {
  example: figma.code`AppButton("${title}", style: ${style}, action: {})${disabled ? figma.code`
    .disabled(true)` : null}`,
  imports: ['import DesignSystem'],
  id: 'app-button',
}
```

Swift-relevant parts of the template API:

- `getString`, `getBoolean`, `getEnum` and `getInstanceSwap` read the instance's properties. Figma property names and variant options must match exactly.
- `getEnum` returns `undefined` for an option missing from its mapping, which leaves a broken argument in the rendered Swift. Map every option.
- `getString` returns the designer's text as is. Escape backslashes, quotes and line breaks (`\n`, `\r`) before placing it inside a Swift string literal, as the example does.
- A nested connected instance renders through `executeTemplate().example`. For children, map the `findConnectedInstances(...)` results with `.map(c => c.executeTemplate().example)` first, then pass that list to `figma.helpers.swift.renderChildren(children, '    ')`. The helper only indents the children's non-empty lines; you write the enclosing `VStack { … }` around it yourself.
- A child template sets `metadata: { nestable: true }` in its export so its code renders inline in the parent's snippet. With `nestable: false`, it displays as a clickable link.
- A slot that maps to a `@ViewBuilder` parameter uses `getSlot('Content')`.
- Compose snippets only inside a template tag: `figma.code`, or `figma.swift`, the Swift-specific tag that Figma's Swift helper example uses. Both are valid. String concatenation breaks the rendered result.

Check the snippet, then publish:

```bash
npx figma connect preview CodeConnect/AppButton.figma.ts --inspect   # properties and variants
npx figma connect preview CodeConnect/AppButton.figma.ts --unique    # every distinct snippet
npx figma connect publish --dry-run
npx figma connect publish
npx figma connect unpublish --node "<node URL>" --label SwiftUI
```

`preview` renders through Figma's API, so it needs the token and network access too. It is not an offline check. Publishing and unpublishing write to the shared Figma library. Run them only when the task asks for it or authorization covers it. `unpublish` without `--node` removes every connection in the project.

**CI:** Figma's documented pattern publishes on merge to the main branch with `npx figma connect publish --exit-on-unreadable-files`, restricted to changes under the template paths. The token comes from a CI secret. For CI, Figma recommends a Plan Access Token over a personal token. Adding that workflow and its secret is a separate `cicd` change.

## Route B — Code Connect UI

Open the published library in Dev Mode, then go to Library → *Connect components to code*. For each component, enter its path (for example `Sources/DesignSystem/AppButton.swift`) and name, or pick them from a connected GitHub repository. Add the same component again for UIKit or another framework. *Add instructions for MCP* stores usage guidance that the MCP server sends to agents.

**When this route shines:** mapping happens in Figma without a code change, and the MCP server gets the component reference immediately.

**When the CLI wins:** you want Dev Mode to show a property-accurate snippet, and you want the mapping reviewed in the same PR as the SwiftUI change.

References: https://developers.figma.com/docs/code-connect/code-connect-ui-setup/ · https://developers.figma.com/docs/code-connect/code-connect-ui-github/

## Legacy SwiftUI parser files

Recognize these when you inspect an existing repo. Typical signs are a `Figma` product from `https://github.com/figma/code-connect` in `Package.swift` or the Xcode project, `*.figma.swift` files, and `xcodeprojPath`, `swiftPackagePath`, `sourcePackagesPath` or `importMapping` in `figma.config.json`. Each connection is a struct that conforms to `FigmaConnect`:

```swift
import Figma
import SwiftUI

struct AppButton_connection: FigmaConnect {
    let component = AppButton.self
    let figmaNodeUrl = "https://www.figma.com/design/<fileKey>/<fileName>?node-id=12-34"

    @FigmaString("Label")
    var title: String = "Save"

    @FigmaEnum("Variant", mapping: [
        "Primary": AppButtonStyle.primary,
        "Secondary": AppButtonStyle.secondary,
    ])
    var style: AppButtonStyle = .primary

    @FigmaBoolean("Disabled", hideDefault: true)
    var disabled: Bool = false

    @FigmaInstance("Icon")
    var icon: Image? = nil

    var body: some View {
        AppButton(self.title, style: self.style, icon: self.icon, action: {})
            .disabled(self.disabled)
    }
}
```

- `@FigmaString`, `@FigmaBoolean` (with an optional `mapping:` to non-Bool values) and `@FigmaEnum` map properties. `hideDefault: true` leaves out a modifier while the property holds its default. `@FigmaInstance` maps an instance-swap property.
- `@FigmaChildren(layers: ["Row"]) var rows: AnyView? = nil` renders nested instances by layer name. Each nested component needs its own connection.
- `let variant = ["Variant": "Destructive"]` on a second struct with the same `figmaNodeUrl` maps that variant to a different code component. `.figmaApply(isDestructive) { $0.tint(.red) }` maps a property to a modifier.
- `#Preview { AppButton_connection() }` reuses the connection as an Xcode Preview.

The parser reads `body` as text and substitutes the mapped values. It does not run the code. Migrate these files before you change a mapping. Do not add new ones.

References: https://developers.figma.com/docs/code-connect/swiftui/ · https://developers.figma.com/docs/code-connect/templates-migration-guide/

## Bidirectional with the MCP server

When the Figma MCP server is connected, inspect the active provider's tool schemas first. Tool names and parameters vary by provider.

- **Read existing mappings:** `get_code_connect_map` with the `fileKey` and `nodeId` from a node URL. It returns the connected code component's name and source, plus a snippet when one exists. Filter by label when the repo publishes several frameworks. Reuse the mapped component instead of generating a new one.
- **Add a mapping:** `add_code_connect_map` writes the node, source path, component name and label (for example `SwiftUI`) to Figma immediately. Without a template, it records only the path and name, like a Code Connect UI mapping. This is an external write, so it needs the same authorization as `publish`.
- `get_code_connect_suggestions`, `get_context_for_code_connect` and `send_code_connect_mappings` are called by Figma or its `figma-code-connect` skill. That skill writes `.figma.ts` template files, which you then review and publish with the CLI. When the provider exposes the skill, load it instead of calling these tools directly.

Reference: https://developers.figma.com/docs/figma-mcp-server/tools-and-prompts/

## Self-review before publishing a mapping

- [ ] New mappings are template files. No new `FigmaConnect` parser structs were added, and existing ones were migrated or left untouched.
- [ ] `include` matches only template files and `.figma.batch.json` files, and covers every batch JSON file.
- [ ] `preview --inspect` shows the same property names and variant options the template reads, and every variant option appears in its `getEnum` mapping.
- [ ] Text from `getString` is escaped before it goes into a Swift string literal.
- [ ] You checked every snippet `preview --unique` renders and each one is valid Swift. The CLI syntax-checks only Prettier-supported languages, so it returns Swift unchecked.
- [ ] The snippet uses *the real component* and its public API, not a stripped-down version. Designers and agents will copy it.
- [ ] The `url=` comment points at the *current* component node (right-click → *Copy link to selection*), not a snapshot taken before the component moved.
- [ ] The label matches what the repo already publishes, so `unpublish --label` and MCP filtering still find it.
- [ ] No secrets in the snippet, the config or the repo. Snippets are visible to anyone with file access, and the token lives only in the environment or a CI secret.
- [ ] Publishing or `add_code_connect_map` was requested or authorized. It changes the shared library for everyone.
